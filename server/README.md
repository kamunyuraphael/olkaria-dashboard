# Olkaria Dashboard — server

Express + TypeScript backend for the CO₂ ANN and AERMOD Dispersion upload
modules. See **API_CONTRACT.md** for the concrete request/response shapes.

## Why two processes

Both analyses are genuinely slow (CO₂ ANN ~3 min, AERMOD ~8-10 min per the
analysis team), so this isn't a plain request/response API — it's a job
queue (BullMQ + Redis) with Mongo as the durable status/result store:

- `npm run dev` — the HTTP API (`src/server.ts`): accepts uploads, enqueues
  jobs, answers `GET /jobs/:jobId` polls.
- `npm run worker` — the job processor (`src/worker.ts`): picks jobs off
  the queue, calls the analysis-service, writes the result back.

Run both side by side in development. Deploy as two separate
processes/services in production — a stuck 10-minute AERMOD run shouldn't
share a process (or a restart) with the API that's answering polls.

## Setup

```bash
cp .env.example .env   # fill in MONGO_URI / REDIS_URL for your environment
npm install
npm run dev             # terminal 1 — HTTP API on :4000
npm run worker          # terminal 2 — job processor
```

Requires a running MongoDB and Redis (`REDIS_URL` in `.env.example` assumes
`redis://localhost:6379`).

## Structure

```
src/
├── config/       env.ts (zod-validated), db.ts, redis.ts
├── types/        domain.ts — ModuleType, JobStage, shared enums
├── models/       User, AccessRequest, AnalysisJob (unified job doc),
│                 Co2AnnResult, DispersionResult
├── middleware/    auth.middleware.ts (JWT, requireAuth/requireAdmin), upload.middleware.ts (multer)
├── services/      token.service.ts, analysisServiceClient.ts (the real
│                  seam to the Python analysis-service for co2-ann and
│                  dispersion — see analysis-service/)
├── scripts/       seedAdmin.ts — bootstraps the first admin user
├── queue/         analysisQueue.ts — BullMQ queue definitions
├── workers/       co2Ann.worker.ts, dispersion.worker.ts
├── controllers/   auth.controller.ts, co2Ann.controller.ts, dispersion.controller.ts
├── routes/        auth.routes.ts, co2Ann.routes.ts, dispersion.routes.ts, index.ts
├── app.ts         Express app (no listen — used by server.ts, testable standalone)
├── server.ts      HTTP API entrypoint
└── worker.ts      job-processor entrypoint (separate process)
```

## First run

```bash
npm run seed:admin   # ADMIN_EMAIL=... ADMIN_PASSWORD=... npm run seed:admin
```

Creates the first admin account — every other account comes from that
admin approving a `POST /api/auth/request-access` submission
(`POST /api/auth/access-requests/:id/approve`). No self-service signup.

## Known sandbox limitation — full Mongo e2e

Everything that doesn't need a live Mongo connection has been verified
directly in this environment: both TypeScript projects typecheck clean,
the auth logic (JWT sign/verify, bcrypt hash/compare) was exercised
directly, and the analysis-service was hit over real HTTP for both
modules. The full chain — `POST /api/auth/request-access` → admin approves
→ login → upload/submit → BullMQ → worker → analysis-service → Mongo →
`GET /jobs/:jobId` poll → UI — has **not** been run end-to-end here: this
sandbox's outbound network allowlist blocks `fastdl.mongodb.org` (where a
real `mongod` binary would come from, including via
`mongodb-memory-server`), and this account's MongoDB Atlas organizations
don't have MCP access enabled, so there's no reachable Mongo instance in
this environment at all — not a bug, just nothing available to connect to.

To run it for real: `cp .env.example .env`, point `MONGO_URI` at any real
MongoDB (local `mongod`, Atlas, etc.), `npm run seed:admin`, then
`npm run dev` + `npm run worker` in separate terminals. A quick smoke test:
```bash
curl -s -X POST localhost:4000/api/auth/request-access -H 'Content-Type: application/json' \
  -d '{"name":"Test","email":"test@example.com","institution":"X","role":"researcher","purpose":"testing"}'
# then, as the seeded admin: log in, GET /api/auth/access-requests, POST .../approve
```
